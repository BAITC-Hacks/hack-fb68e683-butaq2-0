# Butaq — голосовой маршрутизатор страховых обращений

Проект для кейса **Voice Router** хакатона HackAlem AI / Halyk Bank. Butaq принимает голосовой или текстовый запрос, выбирает сценарий из активного каталога и ведёт клиента по его шагам: собирает обязательные параметры, выполняет чтение и расчёты, запрашивает подтверждение и возвращает прозрачный синтетический результат. Поставляемый каталог относится к страхованию, но движок не зависит от его ID или предметной области.

## Что реализовано

- Голосовой и текстовый диалог в браузере на странице `/voice/`: потоковая расшифровка речи, озвученный ответ, возможность прервать ответ и сменить тему. При ошибке потокового соединения доступна отправка текста через обычный HTTP-запрос по явному действию пользователя.
- Три управляемых этапа: **Router** выбирает сценарий и извлекает явно названные слоты, детерминированный **Workflow** валидирует их и управляет подтверждением, **Resolution** формирует короткий ответ только из каталога, knowledge base и результатов action adapters.
- Учёт контекста разговора: активного сценария, его собранных слотов, статуса, отложенных тем и последних реплик. Отсутствующий параметр запрашивается внутри сценария и не считается причиной для handoff.
- Безопасная end-to-end симуляция 31 действия стартового набора: поиск, расчёты, подготовка полиса или обращения, запись, отправка и handoff. Исходный mock backend не изменяется, а синтетические номера живут только в сессии.
- Панель `/admin/` для изменения сценариев, промптов, модели, порога уверенности и workflow-политик, а также атомарного импорта всех JSON-частей набора. Доступ реализован по токену, passkey (WebAuthn) и Face ID (InsightFace).
- HTTP API для текстовых и файловых голосовых запросов и WebSocket API для потокового разговора. Адаптер входящих звонков SignalWire подключён к общему RouterService и включается через `TELEPHONY_ENABLED`; подробнее в [документации телефонии](docs/telephony.md).

## Как работает решение

1. Пользователь говорит или вводит сообщение на `/voice/`. В потоковом режиме браузер передаёт звук по WebSocket, а сервер получает промежуточную и финальную расшифровку через OpenAI. Для файлового API `/router/voice` сначала распознаётся завершённая аудиозапись.
2. Router получает текст, состояние беседы и актуальные сценарии из PostgreSQL. Он не знает заранее ни домен, ни идентификаторы: выбор делается по описаниям, границам и приоритетам загруженного каталога.
3. Workflow читает схемы слотов и действий из тех же настроек, валидирует значения, задаёт по одному вопросу и запускает только зарегистрированные адаптеры. Необратимое действие сначала получает preview и явное «да»/«иә».
4. Resolution озвучивает результат. `simulate` означает завершённую демо-операцию без записи во внешнюю систему; handoff только готовит очередь и резюме контекста.
5. Интерфейс показывает сценарий, объяснение, собранные и недостающие слоты, action trace и задержки. Изменения в admin применяются со следующей реплики.

## Технологии и архитектура

| Компонент | Реализация |
| --- | --- |
| Интерфейс | TypeScript, React, Next.js, Tailwind CSS; браузерные AudioWorklet и Web Audio API |
| Backend и API | Python, FastAPI, WebSocket; пакет `app/` |
| AI-маршрутизация | OpenAI Agents SDK, Router → детерминированный Workflow → Resolution в `multi-agent/`; модель и политики меняются в админ-панели |
| Речь | OpenAI API: потоковая транскрипция через `MULTI_AGENT_TRANSCRIBE_MODEL`, файловая через `V2V_TRANSCRIBE_MODEL`, синтез через `V2V_TTS_MODEL`; код в `multi-agent/` и `v2v/` |
| Данные | PostgreSQL, SQLAlchemy, Alembic; каталог, настройки и записи для Face ID |
| Доступ администратора | Токен, WebAuthn/passkey, InsightFace и ONNX Runtime для локального распознавания лица (`faceid/`) |
| Развёртывание | Docker Compose: backend, PostgreSQL, статический frontend под Caddy; Caddy проксирует `/router/*` на API |

Схема основного пути: **браузер/SignalWire → Caddy/FastAPI → распознавание речи → Router → Workflow/Action simulation → Resolution → синтез речи → клиент**. Активные scenarios, slots, actions, knowledge и mock backend читаются из PostgreSQL на каждом ходе; файлы используются только для первоначального seed. Контекст хранится в памяти backend, а `telephony/` и `app/phone/` подключают входящие звонки через GPT-Live к тому же RouterService.

## Установка и запуск

Нужны **Docker с Compose**, Git и ключ OpenAI API с доступом к моделям, указанным в [`.env.example`](.env.example). Выполните в корне репозитория:

```bash
cp .env.example .env
# В .env укажите реальные V2V_API_KEY, ROUTER_ADMIN_TOKEN и POSTGRES_PASSWORD.
# Для локальной проверки оставьте FRONTEND_ORIGINS и ROUTER_WEBAUTHN_ORIGIN
# со значениями localhost из .env.example.
make up
docker compose ps
```

После запуска откройте **http://localhost:3000/voice/** (страница проекта — http://localhost:3000/). Backend доступен на `http://localhost:8000`, документация API — на `http://localhost:8000/docs`. При старте backend применяет миграции и сразу заполняет пустую БД полным стартовым набором. Веб-камере и микрофону требуется разрешение браузера; доступ к микрофону разрешён на localhost или по HTTPS.

Остановить сервисы можно командой `make down` (том PostgreSQL сохраняется); логи — `make logs`. Для запуска на сервере установите `ROUTER_WEBAUTHN_ORIGIN` в точный публичный origin и добавьте его в `FRONTEND_ORIGINS`. На уже заполненной базе `ROUTER_MODEL` и `ROUTER_CONFIDENCE_THRESHOLD` из `.env` **не перезаписывают** сохранённые настройки: изменяйте их на `/admin/` или через API. Файл `.env` содержит секреты и не должен попадать в Git.

## Как проверить решение

1. Убедитесь, что API отвечает:

   ```bash
   curl http://localhost:8000/health
   # {"status":"ok"}
   ```

2. Откройте http://localhost:3000/voice/. При первом обращении загрузится стартовый каталог из 40 сценариев. Нажмите **Talk to Butaq** и скажите: «Хочу оформить ОГПО». Агент последовательно запросит регион, тип машины, ИИН водителей, госномер и телефон, покажет preview и попросит подтверждение. Карточка справа отображает собранные слоты и действия.
3. Альтернатива без микрофона — отправить текст напрямую:

   ```bash
   curl -sS http://localhost:8000/router/text \
     -H 'Content-Type: application/json' \
     -d '{"session_id":"jury-demo","text":"Хочу оформить ОГПО","synthesize":false}'
   ```

   Ответ дополнительно содержит `workflow_status`, `collected_slots`, `missing_slots`, `confirmation_required`, `action_trace` и `completed`. Доступный каталог можно посмотреть через `GET /router/scenarios`; панель администратора — на http://localhost:3000/admin/.

Для проверки без платных вызовов моделей в локальном окружении доступны тесты (нужны Python, Node.js и запущенный PostgreSQL):

```bash
python3 -m venv .venv
source .venv/bin/activate
pip install -e '.[dev]'
TEST_DATABASE_URL=postgresql+psycopg://butaq:YOUR_POSTGRES_PASSWORD@localhost:5433/butaq python -m pytest -q
cd frontend && npm ci && npm run typecheck && npm run test:voice
```

Тесты backend создают изолированную схему в PostgreSQL; для проверки модели и звука применяются заглушки. Пароль в `TEST_DATABASE_URL` должен совпадать с `.env`.

Полный live-прогон 104 размеченных реплик и 10 диалогов выполняет платные запросы к настроенной модели:

```bash
python case_2/voice_router_dataset/evaluate_live.py \
  --base-url http://localhost:8000 --dialogs --report /tmp/butaq-live-report.json
```

Подробная последовательность настройки, импорта и демонстрации приведена в [demo runbook](docs/demo-runbook.md), а проверка по пунктам исходного ТЗ — в [матрице соответствия](docs/tz-compliance.md).

## Данные и внешние сервисы

- При первом запуске backend пустая база атомарно заполняется **всеми JSON-данными** из `case_2/voice_router_dataset/`: 40 сценариями, 43 слотами, 31 действием, knowledge base, синтетическим backend, 104 тестовыми репликами и 10 диалогами. Повторный запуск не перезаписывает правки; после seed источником истины становится PostgreSQL.
- В `app/data/prod/{auto,health,travel}/` лежат три независимых синтетических набора (авто-, медицинское и туристическое страхование). Они **не загружаются автоматически**: администратор может импортировать один согласованный набор через `POST /router/admin/catalog/import-files`. Подробности — в [описании данных](app/data/README.md).
- Внешний OpenAI API нужен для распознавания речи, работы агентов и озвучки; доступность и стоимость зависят от выбранных моделей и учётной записи. InsightFace при первом использовании загружает локальную модель распознавания лиц. Исходный шаблон главной страницы также использует внешние медиа- и шрифтовые ресурсы.
- Интеграция с SignalWire/OpenAI для входящих звонков описана в [docs/telephony.md](docs/telephony.md), и включается через `TELEPHONY_ENABLED=true` после настройки credentials и вебхуков.

## Известные ограничения

- Все данные синтетические. Workflow проходит сценарий до конца и возвращает preview/результат, но `simulate` не изменяет mock backend и не выполняет оплату, выпуск, отмену, отправку или запись в реальной системе.
- `handoff` срабатывает только по просьбе клиента, условию сценария, настроенному числу неуверенных маршрутизаций или невосстановимой ошибке. Он формирует очередь и контекст, но не соединяет с живым оператором.
- Контекст разговора находится в памяти одного процесса backend и пропадает после перезапуска. Оценка уверенности приходит от модели, не является статистически откалиброванной вероятностью; время ответа зависит от сети и OpenAI, без гарантированных задержек.
- Распознавание лица по изображению подвержено подмене; для более надёжного входа поддерживаются passkey. Для работы голосового сценария нужны интернет и доступ к внешним моделям.
