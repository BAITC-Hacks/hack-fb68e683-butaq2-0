Проект для кейса **Voice Router** хакатона HackAlem AI / Halyk Bank. Butaq принимает голосовой или текстовый запрос, выбирает сценарий из активного каталога и ведёт клиента по его шагам: собирает обязательные параметры, выполняет чтение и расчёты, запрашивает подтверждение и возвращает прозрачный синтетический результат. Поставляемый каталог относится к страхованию, но движок не зависит от его ID или предметной области.

## Что реализовано

- Голосовой и текстовый диалог в браузере на странице `/voice/`: потоковая расшифровка речи, озвученный ответ, возможность прервать ответ и сменить тему. При ошибке потокового соединения доступна отправка текста через обычный HTTP-запрос по явному действию пользователя.
- Три управляемых этапа: **Router** выбирает сценарий и извлекает явно названные слоты, детерминированный **Workflow** валидирует их и управляет подтверждением, **Resolution** формирует короткий ответ только из каталога, knowledge base и результатов action adapters.
- Учёт контекста разговора: активного сценария, его собранных слотов, статуса, отложенных тем и последних реплик. Отсутствующий параметр запрашивается внутри сценария и не считается причиной для handoff.
- Безопасная end-to-end симуляция 31 действия стартового набора: поиск, расчёты, подготовка полиса или обращения, запись, отправка и handoff. Исходный mock backend не изменяется, а синтетические номера живут только в сессии.
- Панель `/admin/` для изменения сценариев, промптов, модели, порога уверенности и workflow-политик, а также атомарного импорта всех JSON-частей набора. Доступ реализован по токену, passkey (WebAuthn) и Face ID (InsightFace).
- HTTP API для текстовых и файловых голосовых запросов и WebSocket API для потокового разговора. Адаптер входящих звонков SignalWire подключён к общему RouterService и включается через `TELEPHONY_ENABLED`; подробнее в [документации телефонии](docs/telephony.md).

## Как работает решение

1. Пользователь говорит или вводит сообщение на `/voice/`. В потоковом режиме браузер передаёт звук по WebSocket, а сервер получает промежуточную и финальную расшифровку через OpenAI. Для файлового API `/router/voice` сначала распознаётся завершённая аудиозапись.
2. Router получает текст, состояние беседы и актуальные сценарии из PostgreSQL. Он не знает заранее ни домен, ни идентификаторы: выбор делается по описаниям, границам и приоритетам загруженного каталога.
3. Workflow читает схемы слотов и действий из тех же настроек, валидирует значения, задаёт по одному вопросу и запускает только зарегистрированные адаптеры. Необратимое действие сначала получает preview и явное «да»/«иә».
4. Resolution озвучивает результат. `simulate` означает завершённую демо-операцию без записи во внешнюю систему; handoff только готовит очередь и резюме контекста.
5. Интерфейс показывает сценарий, объяснение, собранные и недостающие слоты, action trace и задержки. Изменения в admin применяются со следующей реплики.

## Какую проблему решает

Страховые обращения часто похожи по формулировке, но требуют разных действий: проверить статус выплаты, оспорить её сумму или сообщить о новом страховом случае. В одном разговоре клиент может менять тему, возвращаться к предыдущему вопросу и переключаться между русским и казахским.

Butaq сопоставляет запрос с каталогом сценариев через LLM, учитывает контекст беседы и запрашивает уточнение при недостаточной уверенности. Для демонстрации доступны браузерный диалог и панель администратора; для входящих телефонных звонков реализован отдельный адаптер.

## Как работает решение

Пример входного запроса: **«По заявке DEMO-A-2001 деньги списались, а полиса нет»**.

1. **Ввод.** Пользователь начинает голосовой разговор или вводит текст. В основном голосовом режиме звук идёт между браузером и GPT-Live по WebRTC; сервер управляет сеансом и получает события разговора.
2. **Выбор сценария.** Страховой вопрос передаётся Router вместе с контекстом беседы и актуальным каталогом из PostgreSQL. Агент определяет язык, намерение, параметры и возможные отложенные темы.
3. **Проверка решения.** Код проверяет структурированный ответ, допустимость ID и порог уверенности. Результат — `route` (выбран сценарий), `clarify` (нужно уточнение) или `handoff` (нужна помощь оператора).
4. **Подготовка ответа.** Resolution получает выбранный сценарий, связанные справочные сведения и разрешённые инструменты чтения. В примере демозапись сообщает, что оплата получена, а выпуск полиса ещё не подтверждён.
5. **Результат.** Пользователь получает объяснение; голосовой слой озвучивает ответ, интерфейс показывает подписи и решение маршрутизатора. Следующая реплика использует контекст текущего сеанса.

Для файлового API путь отдельный: **аудиофайл → транскрипция → Router → Resolution → синтез речи**. Для текста через HTTP синтез включается параметром `synthesize`.

## Установка и запуск

### 1. Подготовить окружение

Нужны **Docker с Compose v2**, доступ к интернету для сборки и ключ OpenAI API. Команды выполняются из корня клонированного репозитория. Локальные Python и Node.js для Docker-запуска не требуются.

```bash
# Для новой установки. Если .env уже существует, отредактируйте его.
cp .env.example .env
```

Заполните в `.env`:

```dotenv
V2V_API_KEY=ваш-ключ-api
ROUTER_ADMIN_TOKEN=ваш-длинный-случайный-токен
POSTGRES_PASSWORD=ваш-пароль-postgresql
```

Для локального запуска оставьте `ROUTER_WEBAUTHN_ORIGIN=http://localhost:3000`, localhost в `FRONTEND_ORIGINS` и `TELEPHONY_ENABLED=false`. Полный список настроек с пояснениями — в [`.env.example`](.env.example). Ключи хранятся на backend; `.env` не следует добавлять в Git.

## Ограничения

- **Демонстрационные операции.** Нет подключения к реальной страховой системе, выпуска и изменения полисов, выполнения платежей, записи на приём или отправки документов.
- **Передача оператору.** `handoff` сообщает о необходимости помощи человека; фактический перевод звонка и исходящие звонки не реализованы.
- **Зависимость от провайдеров.** Голосовой режим требует совместимого браузера, разрешения на микрофон, сети и доступных моделей. Наличие адаптера SignalWire и тестов с заглушками не подтверждает успешный реальный звонок.
- **Память сеансов.** Активные разговоры и звонки хранятся в одном процессе и теряются при перезапуске. Общего хранилища сеансов для нескольких backend-процессов нет.
- **Качество и измерения.** Уверенность — оценка модели, а не откалиброванная вероятность. Нет подтверждённой метрики на скрытом наборе жюри или гарантии задержки. В Live-режиме времена Router/Resolution не равны времени до первого слышимого ответа; нули для отдельных STT/TTS-этапов не означают мгновенное распознавание и озвучку.
- **Аутентификация по лицу.** Сопоставление изображения само по себе не подтверждает присутствие живого человека. Проверки OpenAI assist опциональны и выключены по умолчанию; также доступен вход по passkey.
- **Разные наборы данных.** Демоидентификаторы `DEMO-*` и сценарии `S*` относятся к каталогу Butaq. Они не совпадают с `SC*` и записями Saqta; импорт каталога не обеспечивает полную реализацию требований другого набора.
